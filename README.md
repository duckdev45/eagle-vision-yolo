# eagle-vision

工項辨識資料集與模型。獨立於產品之外的本機專案（SPEC v1）。

## 一次性設定

```bash
uv sync
cp .env.example .env      # 填 PMS_EMP_ID / PMS_PASSWORD
```

資料來源走 PMS REST API（與前端 orval 同一份契約
`https://pms.example.invalid/api-docs-json`），不需要 DB 或 S3 憑證。

### 2026-08-25：切到正式版

`API_BASE_URL` 從 `pms-dev` 改成 `pms`。dev 是 prod 的複本，`dailyReportInfoId`
與 `fileId` **兩邊完全相同**（實測抽樣 12 份 173 張，重疊 173/173），所以：

- 照片一張都不用重下（實測 `downloaded: 0`）
- 641 張已標註、36 筆複核裁決全部原地生效，不需要重標

真正的差別在母體：**prod 只有 2026-08-01 之後的日報**，dev 另外留著 7/23 起的 81 張
（含 `Project A`、`發大財` 這種測試資料）。照舊的 `merge_manifest` 邏輯跑一次全量，
那 81 張會因為「正式版清單裡查無此人」被集體標成 `active=false`，
其中 **60 張是已標註的訓練照片**——訓練集無聲少掉 9%，而且沒有任何警告。

所以 manifest 多一欄 `apiHost`，`merge_manifest` 只作廢**同一台主機**的照片。
換機器不等於照片消失。切換前抄的舊列 backfill 成 `pms-dev.example.invalid`，
沒有這一欄的一律當 `unknown`，永遠不自動作廢。

要切回 dev 就改 `.env` 的 `API_BASE_URL`，兩邊的照片會並存在同一份 manifest 裡，
用 `apiHost` 分得出來。

## 操作台（建議入口）

```bash
uv run streamlit run src/app.py
```

同步、看分佈、翻照片、複核佇列、歷史資料、改 `labels.yaml`、看混淆矩陣都在裡面。
照片頁**最新加入的排最前面**（manifest 是 append-only，原順序等於最舊的在最前，
每天看的都是同一批老照片）。

「⑤ 歷史資料」= 舊 pptx 那批的去重統計、補了哪些類別、
**以及它到底有沒有進線上那組訓練集**（讀 split JSON 的 `trainLegacy`，不用去猜）。

「④ 複核佇列」= 任一參考答案與 title 不一致的照片配上熱區，人裁決寫進 `data/review.csv`。
裁完之後要從上面第 4 步開始重跑，裁決才會進到模型裡。

#### 三個參考答案，照「誰寫的」排序

| 來源 | 誰產的 | 涵蓋 | 與規則一致率 | 能當答案嗎 |
|---|---|---|---|---|
| `feMeta.pool[].label`（`custom: true`） | **工地主任自己打的**查驗重點 | 543 條 | 92%（扣掉沒訊號的） | ✅ |
| `feMeta.specKey` | **人在前端點選的**工種 | 138 張 | **98.6%**（136/138） | ✅ 但只到工種 |
| `anno.workItem` | Gemini 答的 | 約 180 張 | — | ❌ 只能當提示 |
| 探針的預測與**邊際** | 上線那顆模型 | 全部 | — | ❌ 這是被考的人 |

前兩個是人寫的，與規則不一致時**排在佇列前面**——規則錯的機率遠高於 Gemini 不一致。
第三個是受測者的作答，拿它當考卷答案是 SPEC §7.2 明文禁止的。

#### 分四層，不是加總分數

前三種問「標籤對不對」，第四種問「模型會不會」——兩件事不一樣，混成一個分數就看不出
該先看哪一批。實測 520 張的分佈：

| 層 | 訊號 | 張數 |
|---|---|---|
| 4 | 人寫的有異議（chips / specKey） | 27 |
| 3 | 模型與 Gemini 都不同意 title | 7 |
| 2 | 只有 Gemini 有異議 | 24 |
| 1 | **模型難分**（top1 − top2 邊際 < 0.25，僅測試集） | 7 |

第 1 層就是主動學習那一塊。用**邊際**而不是信心：信心 0.9 但第二名 0.85 代表模型
在兩類之間猶豫，信心 0.5 而第二名 0.05 反而很篤定。**只在測試集上算**——訓練集那
400 張模型背過，邊際再小也是假的猶豫。

沒有這一層的話，520 張裡有 462 張（89%）三個參考答案都一致，模型在上面答錯也沒人
會看到——佇列問的是「標籤對不對」，不是「模型對不對」。

`chipsOn` 落到 fallback **不算**不一致——查驗重點寫的是「素地清理是否乾淨」這種驗收
條件，本來就不含工種詞，套規則當然標不出來。那是「沒訊號」，不是「有異議」；
不濾掉的話佇列會從 27 張暴增到 111 張，全是假警報。

它們的用途不是取代 title（實測只多救回 4 張），是**對帳**。

#### 標框：讓模型學「該看哪」

複核卡片上的「✎ 標框」用滑鼠拖出證據區域。框的用途**不是註記，是訓練資料**：

```
人拖的框 → review.csv 的 box 欄（0~1000 相對原圖，與 Gemini evidence 同格式）
        → features.py --crops：裁那塊、重新編碼
        → split.py：以 `{fileId}#{i}` 併進 train，掛同一個標籤
```

為什麼這樣用：線性探針吃的是**整張圖**的 embedding，框塞不進去。但把框裡那塊單獨
編碼一次、掛同一個標籤，等於告訴模型「這個類別長這樣，不是整張場景長這樣」。
`1F人行道地磚貼飾` 那張整張餵下去，最強的訊號是右側行道樹（實測熱區就壓在那）；
只餵框住地磚的那塊，訊號就只剩地磚。

**裁切塊只進 train。** 母張若落在測試日，它的裁切塊一併排除——那等於把答案偷渡到
訓練側（`test_crops_never_leak_from_test_photos` 擋著）。

驗證有沒有效的方法是現成的：重訓後跑 `explain.py --probe`，看熱區與人標框的重疊
有沒有上升（`explain.iou()` 已經在算模型框 vs Gemini 框，同一條路）。

## 命令列

```bash
uv run src/sync.py                       # 每日同步（cron）
uv run src/legacy.py --dry-run           # 掃舊版 pptx 日報（第三個資料源，先試跑）
uv run src/organize.py                   # 建照片結構樹
uv run src/prepare.py                    # 四角遮蔽
uv run src/split.py                      # 工地 × 日期切分
uv run --extra train src/features.py     # 抽 embedding（首次會載 SigLIP 權重）
uv run --extra train src/train.py        # 線性探針
uv run --extra train src/evaluate.py     # 指標 + 混淆矩陣 + Gemini 基準線
uv run --extra train src/explain.py      # 判斷依據：Grad-CAM 熱區（convnext checkpoint）
uv run --extra train src/explain.py --probe   # 判斷依據：遮擋法熱區（線上那顆探針，批次）
uv run tests/test_core.py                # 自檢
```

`--extra train` 才會裝 torch；只跑同步不必裝。

## 新照片進來之後（要重跑模型）

照片一多，標籤分佈、類別門檻、切分全會變，模型必須重訓。

**操作台按鈕**（`make app` → ① 同步）。那頁只有三顆按鈕，各做一件別人不做的事：

| | 按鈕 | 做什麼 | 什麼時候按 |
|---|---|---|---|
| 1 | 同步日報 + 下載照片 | 只抓，**不重訓** | 想知道今天有沒有新照片 |
| 2 | 全鏈重跑 / 只重跑模型 | 切分 → 訓練 → 評估 → 熱區 → 學習紀錄 | 有新照片 / 只改了標籤或裁決 |
| 3 | 建照片結構樹 | 重建 symlink，**跟訓練無關** | 想用檔案總管翻照片 |

第 2 那兩顆的差別只有「要不要先抓新照片」——全鏈 = 第 1 顆的工作 + 前處理 +
embedding，然後才是共同的後半段。

跑完顯示分數，**切換是另一顆按鈕**。注意分數**不能直接跟現在那版比**（見下面
「學習紀錄」的註一，考卷每版都不同）——要比就看 per-class 那節。

> 以前還有一顆「前處理（遮蔽 + 縮圖）」，它是全鏈第 2 步的子集、沒有自己的選項，
> 連說明都寫著「整條鏈看下面」。那不是按鈕是陷阱：按了以為有進度，其實下面還得
> 整條再跑一次。2026-08-25 移除，要單步跑用 `make`。

**終端機**：

```bash
make retrain SPLIT=v9    # 照片有新的：同步 → 遮蔽 → embedding → 切分 → 訓練 → 評估 → 熱區
make model   SPLIT=v9    # 只改了 labels.yaml 或複核裁決：從切分開始就好
make use     SPLIT=v9    # 看過分數，把操作台切到這一版
make help                # 全部 target
```

`SPLIT` 每次給新名字。`make -n` 可以先看它要跑什麼。展開就是下面這七行：

```bash
uv run src/sync.py                                          # 1 抓新日報 + 照片
uv run src/prepare.py                                       # 2 遮蔽 + 縮圖
uv run --extra train src/features.py                        # 3 抽 embedding
uv run src/split.py --name v8                               # 4 重切，標籤凍進 JSON
uv run --extra train src/train.py --split v8                # 5 重訓探針
uv run --extra train src/evaluate.py --split v8 --run v8    # 6 指標 + Gemini 基準線
uv run --extra train src/explain.py --probe --split v8      # 7 重算熱區快取
```

最後 `make use SPLIT=v8`（或操作台上的切換按鈕）—— 這寫進 `derived/splits/CURRENT`，
操作台的「系統判斷」與「判斷依據」都認它。不切的話畫面上還是舊模型
（實測踩過：一直顯示 v1 的 0.712，實際模型已經 0.847）。

幾件容易踩的：

- **第 2、3 步是增量的**，只處理新檔。只有前處理參數改過（改遮罩規則、改長邊）才加
  `--force`，而且**兩步都要加**——影像重做了、embedding 沒重抽，等於拿舊特徵配新圖。
- **每次開新的 split 名字**，別原地覆蓋。標籤一變，同名舊報告的分母就對不上，
  之後會拿兩份不同分母的東西當同一件事比。
- 只改 `labels.yaml`、或只在複核佇列裁決 → **從第 4 步開始**就好，1~3 與標籤無關。
- 第 7 步是因為熱區解釋的是**模型**，模型換了舊熱區就是別人的依據。593 張約 4 分鐘。
- `uv run src/organize.py` 重建 `derived/tree/` 的 symlink，只影響用檔案總管翻照片，
  跟訓練無關，想跑再跑。

## 照片沒進訓練，只有兩種原因

操作台 ⑥ 標籤規則 把兩種並排顯示。它們是不同的問題，處置也不同：

| | 狀況 | 現況 | 怎麼解 |
|---|---|---|---|
| **排隊中** | 規則認得，張數不足 `min_class_size` | 9 類 / 47 張 | **不用做事**，過門檻自動上線 |
| **沒人認領** | 規則根本沒命中 → `fallback` → 丟掉 | 4 張 | 補一條規則（見下一節） |

### 入場門檻是 12 張，算的是 train + test 全部

`min_class_size: 12` 在 `Labeler.apply()` 裡執行，**在切分之前**——所以算的是整個
已標註集合，不是訓練集。一類 12 張（比如 10 train + 2 test）就算達標。

**別跟 `MIN_TRAIN` 搞混**：那是進場**之後**的切分保底（把含稀有類別的測試日整天搬回
train），跟能不能上線無關。兩個都預設 12，純屬巧合。

過門檻會**自動**上線，不用改任何程式——`金屬-欄杆鐵件` 就是這樣在 v18 自己冒出來的
（JOURNAL 第二節標「新類別」）。目前排隊的：

| 類別 | 現有 | 還差 | 最近一張 |
|---|---|---|---|
| 輕隔間 | 8 | 4 | 2026-08-21 |
| 結構-鋼筋 | 8 | 4 | 2026-08-17 |
| 裝修-石材 | 7 | 5 | 2026-08-25 |
| 門窗-鋁門窗 | 6 | 6 | 2026-08-14 |
| 防水-矽利康 / 門窗-玻璃 / 雜項-停車防護 / 雜項-缺失改善 | 4 | 8 | — |
| 雜項-成品保護 | 2 | 10 | 2026-08-08 |

「最近一張」是用來判斷它**還在不在持續進來**的：`裝修-石材` 昨天還有新照片，差 5 張
大概再幾天就上線；`雜項-成品保護` 停在 8/08 快三週沒動，差 10 張可能永遠不會到。

`split.py` 每次重切也會印一行排隊摘要，不必開瀏覽器才看得到。

## 沒有規則認領的照片（`make newclass`）

`drop_fallback: true` 讓規則沒命中的照片不進訓練。那個決定是對的——把互不相干的
東西倒進一個「其他」類，等於教模型「其他 = 一袋雜物」（實測 top-1 0.760 → 0.699）。

**但「不倒進其他」不等於「該丟掉」。** 照片一張都沒被刪，都在 `raw/photos/`，
少的只是一條規則。問題是以前沒人看得到：

- 操作台 ⑥ 有個面板寫著「落入 fallback 的標題 —— 這裡就是下一條規則的來源」，
  它拿的是 `labeled()`，而那條路徑已經先把 fallback 濾掉了 → **從寫出來就一直顯示 0 張**。
- 新工種進來只會表現成「某個類別的張數沒長」，沒人會聯想到是規則缺一條。

現在三處都會出聲：

```bash
make newclass                       # 候選詞 + 可貼的 yaml 區塊
uv run src/newclass.py --src pms    # 只看線上真的會收到的照片
```

`split.py` 每次重切都會警告有幾張沒人認領，操作台 ⑥ 的面板改用 `labels.unclaimed()`
（繞開濾網），並附上候選清單。

候選詞怎麼挑：把沒命中的標題拆成 2~4 字的中文片段，**貪婪覆蓋**——每輪選還沒被
認領的照片裡蓋最多的那個詞。兩道過濾：

- **蓋不到 `min_class_size` 就不提**：加了規則也會被門檻擋下來，白忙一場。
- **通用字扣分**：「施作」「安裝」在已分類的標題裡也一大堆，插一條進去會把既有
  類別整批攔走，而且不會有人發現（規則是第一個命中者勝）。通用度是從資料現算的，
  不是硬編停用詞表——換個工地的用字習慣，表就過期了。

實跑（PMS + legacy 一起 895 張 / 278 種標題），挑出 11 個候選蓋掉 294 張：

| 詞 | 張數 | 例 |
|---|---|---|
| 設裝 | 63 | 1F大廳公設裝修施作 |
| 拉門 | 47 | 2~7F淋浴拉門施作 |
| 櫃安 | 46 | 22F廚櫃安裝 |
| 窗框崁 | 31 | 12F窗框崁縫施作 |
| 戶大 | 21 | 7-3F各戶大門電子鎖按裝 |
| 緣石 | 17 | 1F沿街步道緣石抿石子施作 |
| 鷹架 | 14 | R2F鷹架組立 |
| **植裁** | **13** | **空中花園植裁** ← `植栽` 的錯字，現有類別接不到 |

詞常常是跨詞界的碎片（`櫃安` = 櫥櫃+安裝），因為它蓋得比完整詞多——`櫥櫃` 會漏掉
「廚櫃」那種錯字。**所以標籤名要人自己取**，工具只負責指出「哪個詞蓋得到最多沒人
認領的照片」，不負責決定那是不是一個工種、該掛在工程分類樹哪一支。

PMS 目前只有 4 張沒人認領（木門扇、棄土坑），都不到門檻，所以 `--src pms` 提不出
候選——這是誠實的結果，不是壞掉。

### labels.yaml v6 的結果（2026-08-25）

依候選清單改完規則，沒認領的從 **895 張降到 647 張**。改法分三種：

| 處置 | 內容 | 張數 |
|---|---|---|
| **擴充既有規則** | `廚具`+廚櫃/櫥櫃、`植栽`+植裁（錯字）、`地磚`+道磚/店鋪地 | 104 |
| **新增 5 類** | 防水-嵌縫、門窗-淋浴拉門、門窗-住戶大門、假設-鷹架、公共-路緣石 | 132 |
| **排除** | 消防檢查（看過照片是撒水頭放水測試，屬查驗不是施工） | 12 |

改規則會**搶走既有類別的照片**，一定要先對帳。這次搶了 17 張，看照片確認兩處都是
改對了：`門框崁縫` 11 張從 `門窗-鋁門窗` 移到 `防水-嵌縫`（照片是工人在窗框周邊嵌縫，
樹上明列「鋁門窗框嵌水泥砂漿縫」）、`車道磚抹縫清潔` 4 張從 `雜項-清潔` 移到
`泥作-地磚貼飾`（照片是抹磚縫，不是清潔）。

**63 張的最大宗刻意沒收**：`1F大廳公設裝修施作`。抽 4 張看是木作造型、藝術漆牆面、
完成面、木作櫃體+石材天花——一個 title 蓋整個大廳跨工種。開成一類等於把「其他」
改個名字，正是〈拆掉其他〉那節說不要做的事。那 63 張要靠照片層級的複核裁決拆。

#### 分數：線上模型零影響，新類別不能開

| | 同一份 120 張考卷 top1 | macroF1 |
|---|---|---|
| v22（預設） | **0.8500** | **0.8846** |
| v22L（`LEGACY=1`） | 0.7667 | 0.8281 |

v22 與 v21 **數字完全相同**（0.8443 / 0.8703）——265 張改動全在 legacy，
而預設的類別鎖把 legacy 專屬的新類別擋在外面，所以線上那顆一點都沒動。

開 `LEGACY=1` 讓 5 個新類真的進訓練，top1 掉 8.3pt（遠超 120 張的噪音 σ≈0.033），
18 張改錯只換回 8 張。**壞在 0 張測試樣本的類別上**：18 張裡有 7 張被
`裝修-石材`、`防水-嵌縫`、`雜項-缺失康`、`門窗-淋浴拉門` 這種考卷驗不到的類別吃掉。
`雜項-清潔` f1 從 0.800 掉到 0.533，其中 3 張全被 `裝修-石材` 搶走。

所以規則要留，類別先別開——這正是預設行為。**規則是為將來寫的**：PMS 哪天開始有
淋浴拉門、嵌縫、鷹架的照片，就會自動被接住、自動累積到 `min_class_size` 上線，
不用有人記得回來加規則。

## 稀有類別保底（`MIN_TRAIN` / `LEGACY_FILL`）

按天切分完全不看類別分佈。稀有類別的照片集中在少數幾天，那幾天一落進測試窗口就
整批被抽走——v20 實測 `金屬-欄杆鐵件` **train 6 張 / test 10 張**，考的比訓練的多，
recall 0.700 是餓出來的，不是模型笨。

兩道保底，`make model` 預設都開：

| 旋鈕 | 預設 | 做什麼 |
|---|---|---|
| `MIN_TRAIN` | 12 | 調**切分**：把含稀有類別的測試日**整天**搬回 train |
| `LEGACY_FILL` | 40 | 調**資料**：切完還不足的類別，只從 legacy 補那幾類到門檻 |

搬只能以整天為單位——搬單張就違反鐵律三，同一天同一面牆的另一張還在 test。
三道護欄：每個工地至少留一天測試日、測試集最多縮 15%、只搬**划算**的天
（看那天有幾成是稀有類別，不是看張數）。護欄比保底重要：沒有 `max_shrink` 的
第一版把測試集從 132 砍到 70，搬 4 整天只換到 8 張，而且還是沒到門檻。
**測試集是唯一的量尺，為了餵飽一個類把量尺鋸掉一半是虧的。**

`LEGACY_FILL` 只補 **PMS 已經有的類別**。legacy 那 9 個 PMS 沒有的類
（模板、廚具、石材…）不在這裡開，解鎖新類別是 `LEGACY=1` 的事，是產品決定。
（第一版沒擋，`--legacy-fill 40` 順手把類別數從 11 開成 21，其中 9 類測試集一張都沒有。）

實測 v21（`MIN_TRAIN=12 LEGACY_FILL=40`）vs v20，**同一份 122 張考卷**：

| | v20 | v21 |
|---|---|---|
| top1 | 0.8279 | **0.8443** |
| macroF1 | 0.8455 | **0.8703** |
| `金屬-欄杆鐵件` f1 | 0.857 | **1.000** |
| `設備-電梯` f1 | 0.875 | **0.941** |

top1 +0.016 在 122 張的噪音（σ≈0.033）之內，但**升的正好是補過的那兩類**，
而且 4 張修好、2 張弄壞——機制照設計走，不是擲骰子擲贏的。

## 學習紀錄（`reports/JOURNAL.md`）

`make model` 最後一步自動重寫，也可以單獨 `make journal`（不重算任何東西，只讀
已經生成的報告）。單一個 report 只知道自己的分數，串起來才看得出趨勢：

| 節 | 回答的問題 |
|---|---|
| 一、每次重訓的分數 | 全部 run 的 top1 / macroF1 / Δ，**分母（測試張數）並列**——分數升降有一部分是換考卷換的 |
| 二、學到／退步了什麼 | 最新版 vs 上一版的 per-class F1 差，support 變了會標出來 |
| 三、最弱的類別 | 這一版 f1 最低的六類，配 precision / recall |
| 四、慣犯混淆 | 跨 run 重複出現的「真X→猜Y」。12/12 = 每次重訓都還在錯，那是規則或資料的問題，不是這次運氣差 |
| 五、每次都錯的照片 | 同一張圖連錯幾個 run。要嘛標錯了、要嘛真的難，兩種都該人去看 |

四、五兩節會**低估**——`errors/` 每個 run 只存前 24 張誤判。看完整誤判開
`reports/<run>/confusion.png`。

第五節的 fileId 前 8 碼直接拿去複核佇列搜，裁決完 `make model SPLIT=vN` 就進模型。

#### 去重：13,350 張抽出來，一半是重複的

| 擋掉的 | 張數 | 靠什麼 |

工地名經 `SITE_ALIAS` 對齊 PMS 的 `constrName`（`SITE-C` → `SITE-C`），
否則「同工地同日不跨組」這條鐵律形同虛設。

`reports/2026-08-19-v13/`。同一份測試集、macro-F1 只算測試集真的有樣本的 10 類
（9 個新類 support=0，算進去會被當成 f1=0 拉低平均——那是指標假象，不是退步）：

|---|---|---|---|---|
| 只有 PMS | 442 | 18 | **0.815** | **0.823** |
| PMS + 舊資料（**只限原本 10 類**） | 4,382 | 18 | 0.782 | 0.775 |
| PMS + 舊資料（全部） | 6,001 | 21 | 0.702 | 0.768 |
| PMS + 舊資料（**只加新的 11 類**） | 2,061 | 21 | **0.589** | 0.728 |

最後一列是關鍵：只把 11 個新類別加進去（原本 10 類仍只用 PMS 訓練），

現在 `結構-鋼筋` 測試集有 4 張、`金屬-欄杆鐵件` 2 張，代表工地已經開始拍了；


這是產品決定（覆蓋率 vs 準確率），不是預設值該替人做的。

> 掉分的一半來自類別空間 10 → 21（9 個新類在測試集裡沒有樣本卻照樣搶機率），

取檔鏈（全部只讀）：

母體分佈：防水隔熱 12,278 / 機電 8,952 / 裝修 8,569 / 門窗 4,959，其餘合計 1,895。

小類一張都抽不到。`--per-class-cap 0` 可關掉。

#### 遮罩：兩邊遮不同的東西

兩個系統烤在圖上的東西不同，所以分開遮：

| 資料源 | 遮什麼 | 依據 |
|---|---|---|
| PMS 日報 | 四角，各 30% × 12% | 左上/右上/左下工種膠囊、右下日期標籤 |
| QMS 稽核 | 左下 `0~56% × 60~100%` | 浮水印實測 x 2%~52% / y 65%~97%，留 margin |

這在**兩階段微調**下是安全的：QMS 預訓練與 PMS 微調的資料不在同一個分類器裡競爭，
遮罩形狀無從變成「哪個系統 → 哪個工種」的捷徑。
若哪天要單一分類器混訓，這條要重談（見下方失敗的混訓實驗）。

<details><summary>曾經統一遮罩的代價（已回退）</summary>

QMS 浮水印**烤死在 S3 原檔上**，沒有乾淨版本（實測 x 2%~52% / y 65%~97%，佔 16%）。
所以 `prepare.py` 改成四角 + 左下方塊，**兩個資料源一視同仁**——只遮 QMS 不遮日報的話，
「左下有沒有灰塊」就成了「這張來自哪個系統」的訊號，而系統與工種高度相關。

曾經把兩邊都遮成「四角 + 左下」以防資料源洩漏，代價是日報基準線
**0.818 → 0.768（-5pt）**。改成兩階段微調後這個顧慮消失，已回退，基準線回到 0.818。

#### 三個實驗共用一份切分格式

`split.py` 把 `labels` 直接寫進 split JSON，train/evaluate 不必知道資料來自哪個系統：

```bash
uv run src/split.py            # A 日報：工地 × 日期
uv run src/split.py --qms      # B QMS：按 constructionInsId 整格切
uv run src/split.py --merged   # C 混合：日報 train + QMS 全部 → 測日報 test（測試集原封不動）
```

QMS 一格是同位置同時間拍的 2~3 張，**必須整格切**，拆開等於把近乎同一張分到兩邊。

#### 實驗結果：QMS 照片不能直接混進訓練

抽樣 3,000 張（1,517 格、138 小類、26 個中類 ≥30 張）。測試集**全程固定用日報的 99 張**。

| 實驗 | 訓練資料 | 類別 | top-1 | macro-F1 |
|---|---|---|---|---|
| **A 現況** | 日報 342 | 10 | **0.768** | 0.722 |
| B QMS 自己 | QMS 2,254 | 26 中類 | 0.680 | 0.631 |
| B' 純遷移 | QMS 1,165 | 10（折標籤） | **0.283** | 0.254 |
| C 硬合併 | 日報 + QMS 全部 | 36 | 0.687 | 0.373 |
| C' 折標籤合併 | 日報 + QMS 1,165 | 10 | 0.596 | 0.607 |

劑量曲線（QMS 逐量加入日報訓練集）：

| QMS 加入 | 0 | 100 | 342 | 700 | 1,165 |
|---|---|---|---|---|---|
| top-1 | 0.768 | 0.798 | 0.707 | 0.626 | 0.596 |
| macro-F1 | 0.722 | 0.714 | 0.663 | 0.626 | 0.607 |

**結論：領域偏移嚴重，加得越多掉得越兇。**

- B = 0.680 證明**資料本身沒問題**：QMS 的標籤與影像自己學自己是學得起來的
- B' = 0.283 證明**學不到日報上**：稽核照是「查驗點特寫」，日報照是「工人在現場施工」的廣角，同一個工種在兩邊長得不一樣
- 加 100 張時 top-1 反而漲到 0.798，但 macro-F1 沒跟著漲，且測試集只有 99 張——**當成雜訊看，不要當成證據**

#### 微調也救不回來（`src/finetune.py`）

線性探針是凍結編碼器，吃不下領域差異，所以做了兩階段微調：
QMS 26 中類預訓練 → 換分類頭 → 日報 10 類微調。附「不看 QMS」的對照組。

| 方法 | 訓練資料 | 日報 test top-1 |
|---|---|---|
| **線性探針（現行最佳）** | 日報 342 | **0.818** |
| 微調・不看 QMS | 日報 342 | 0.788 |
| 微調・先看 QMS | QMS 2,254 → 日報 342 | 0.748 |
| （QMS 自己的測試集） | QMS 2,254 | 0.857 |

**先看 QMS 反而更差。** 但 QMS 自己從 0.680（線性探針）漲到 **0.857**（微調），
證明編碼器一鬆綁就吃得下那個領域——它只是吃不到日報這邊來。

`finetune.py` 的 `bestTop1` 是拿測試集挑 epoch 選出來的（模型選擇洩漏），
比較一律看 `finalTop1`，JSON 裡有註記。

#### ⚠ 這些差距都在雜訊裡

測試集只有 99 張，**1 張 = 1.0pt，95% CI 約 ±7.6pt**。
以「工地 × 日期」為群組做 20 次分組交叉驗證：

```
top-1 = 0.775 ± 0.075   (範圍 0.660 ~ 0.976)
單一固定切分的 0.818 落在第 75 百分位 —— 偏樂觀
```

所以上表 0.818 / 0.788 / 0.748 的差距**統計上分不開**。能安全下的結論只有兩條：

1. QMS 這批**沒有任何證據**對日報任務有幫助（三條路都試過：混訓、遷移、預訓練）
2. QMS 自己那條線是實打實的（0.857，不同測試集、596 張，差距夠大）

固定切分留著給跨次實驗比較用；**下判斷時要看分組交叉驗證，不要看單一數字。**

`reference/qms_to_report.yaml` 是 QMS 中類 → 日報類別的對映，只映語意明確相同的 7 個。

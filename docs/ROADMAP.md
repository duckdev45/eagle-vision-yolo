### YOLO11 前置決策（2026-09-01 覆核後定案）

- **尺寸**：v1 用 YOLO11n/s。角色＝工種軸的線性探針——先驗證 8–12 樣態視覺可分，m/l 留給資料量上來後。
- **座標空間**：GDINO 初標、CVAT 標註、YOLO 訓練三方一律掛 raw 原圖（512px derived 細裂縫消失）。注意 imgsz 預設 640——raw 長邊幾千畫素，細小缺失在 640 下照樣會消失，**imgsz/tiling 政策在煙霧測試一併量測**。
- **split 單位＝案場×日期**：沿用 split.py 既有規則（日報 constrId × reportDate 整天切）。照片型缺失同案場同日有視覺相關性（同工班、同批材料、同光源），按單張照片切，G2 的 mAP 會虛高。
- **類別不平衡**：一次全訓，不用 class weight 硬撐；人審框不足下限的類**整批不進 v1 資料集**（沿用 labels.py `min_class_size` 整批 drop 的精神，偵測類下限從數十框起談）——帶爛資料硬訓比不訓更傷 per-class gate。「高頻類先行」是部署順序，不是訓練順序。
- **驗收條件**：訓練集僅收 HUMAN_REFINED 框，純 AI_GUESS 一律排除——yolo_preprocessor 的哲學寫成硬條款。
- **部署形態分兩段**：v1 只上**標註輔助**（離線批次跑 YOLO → 框走 GDINO 同一條 ETL 匯入 CVAT，零部署零漏檢風險）；per-class 線上數據（人審框 vs YOLO 框，免費標籤）量夠了才升級**複核佇列分流**——那時 hard gate 才生效。
- **角色交接**：YOLO11 訓成後回頭取代 GDINO 在 CVAT 迴圈裡對已訓類別的初標角色——GDINO 是冷啟動引擎，不是常駐依賴。

#### GDINO 煙霧測試結論（2026-09-03，執行序 #1 結案：初標工具不定案）

469 張樂氧森照片（單場單日，僅供煙霧測試）分三輪測，每輪都是同一個模式——**GDINO 找得到
「有沒有這個物件」，判不出「這個物件是不是缺失狀態」**：

- v1~v3 詞彙表（43→82 框人審）：`protection` 組 47/50 錯（94%）、`cleanliness` 25 張 88% 錯，
  wrong 均分(0.401) > correct 均分(0.381)——分數沒鑑別力，調門檻無效，問題在模型不在門檻
- 換 tiny→base 模型（同 v3 詞彙表，全 454 張對照）：`crack` 2→32 張真的回血，但
  `damage`/`scratch`/`paint` 依然掛零，`rust` 89→84 框（僅 5 張真標鏽蝕）假陽性照樣氾濫——
  **換大模型救不了死詞，也救不了假陽性**，問題不在模型量級
- 順手修一個真 bug：`infer()` 對 GDINO 回傳短語用字典精確比對，但 GDINO 常回傳截斷/疊字片段
  （如 `floor tile floor tile`），精確比對把真命中當「認不得」全丟。改用詞集合子集比對
  （`resolve_pattern`，唯一候選才採信）後，`scratch`/`damage` 已知真陽性從 0/6 回升 6/6——
  但全量重跑（v4 詞彙表 + bug 修復）`rust` 假陽性不減反增（89→144 框，仍只 5 張真陽性），
  `scratch` 從 0 直接冒出 49 框（9 張真陽性）——**bug 修復同時放大了信號和噪音，物件詞彙
  的假陽性結構性存在，不是比對邏輯或詞彙選字能解的**
- 三個測過詳細數據的樣態（protection/cleanliness/rust）結論一致；scratch 補測後同一結論；
  結構性原因：prompt 短語命中的是「物件是否存在」，樂氧森這批缺失多是「既有物件的狀態異常」
  （生鏽的水龍頭 vs 水龍頭、刮傷的門框 vs 門框），GDINO 的 zero-shot grounding 沒有狀態判斷能力

**GDINO 從「初標主力」降為停用**——冷啟動角色需要換人接手，候選方向見待決事項。
`src/fr_gdino.py` 保留（`resolve_pattern` 的比對修復對任何未來重跑都有效，詞彙表 v4 也留著
當參考），但不再是 CVAT 初標的預設路徑，執行序 #6 CVAT 上線的「GDINO 預標匯入」步驟需要
重新設計或改人工冷啟動。

### YOLO11 前置決策（2026-09-01 覆核後定案）

- **尺寸**：v1 用 YOLO11n/s。角色＝工種軸的線性探針——先驗證 8–12 樣態視覺可分，m/l 留給資料量上來後。
- **座標空間**：GDINO 初標、CVAT 標註、YOLO 訓練三方一律掛 raw 原圖（512px derived 細裂縫消失）。注意 imgsz 預設 640——raw 長邊幾千畫素，細小缺失在 640 下照樣會消失，**imgsz/tiling 政策在煙霧測試一併量測**。
- **split 單位＝案場×日期**：沿用 split.py 既有規則（日報 constrId × reportDate 整天切）。照片型缺失同案場同日有視覺相關性（同工班、同批材料、同光源），按單張照片切，G2 的 mAP 會虛高。
- **類別不平衡**：一次全訓，不用 class weight 硬撐；人審框不足下限的類**整批不進 v1 資料集**（沿用 labels.py `min_class_size` 整批 drop 的精神，偵測類下限從數十框起談）——帶爛資料硬訓比不訓更傷 per-class gate。「高頻類先行」是部署順序，不是訓練順序。
- **驗收條件**：訓練集僅收 HUMAN_REFINED 框，純 AI_GUESS 一律排除——yolo_preprocessor 的哲學寫成硬條款。
- **部署形態分兩段**：v1 只上**標註輔助**（離線批次跑 YOLO → 框走 GDINO 同一條 ETL 匯入 CVAT，零部署零漏檢風險）；per-class 線上數據（人審框 vs YOLO 框，免費標籤）量夠了才升級**複核佇列分流**——那時 hard gate 才生效。
- **角色交接**：YOLO11 訓成後回頭取代 GDINO 在 CVAT 迴圈裡對已訓類別的初標角色——GDINO 是冷啟動引擎，不是常駐依賴。

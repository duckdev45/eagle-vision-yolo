## 二、第一個發現：第 4 層有 77 張是假異議（純規則 bug）

第 4 層的定義是「`chipsOn`（工地主任打的查驗重點）套規則出來的類別 ≠ title 套規則出來的類別」。
但 chipsOn 寫的是**驗收條件**，不是施作階段。實測 314 張 tier4 裡：

```
242 張（77%）→ 工種一致，只差「施作內容」那一層
  打底 title 的 chips    → 泥作-粉光    （94 張同一段 chips 文字）
  粉光 title 的 chips    → 泥作-粉光    （同一份文字）
  外牆磁磚 title 的 chips → 泥作-壁磚貼飾 （69 張）
```

**「打底」和「粉光」的查驗重點是同一份文字**——主任打查驗表時根本不分工序階段。
所以這 77 張不是「人說了不同意見」，是「chips 的粒度天生比類別粗」。

對照組：同樣的程式碼對 `specKey` 已經只比工種層級（`d_spec = spec != cls.str.split('-')[0]`），
因為「specKey 只到工種，不能直接當答案」。**chipsOn 的情況一模一樣，卻被拿去比了細類**——
這是 `core/review_utils.py:85` 的不對稱，不是資料問題。

**修法**：`d_chips` 改成與 `d_spec` 同邏輯，只比工種前綴。預期效果：待裁 302 → 228，tier4 109 → 34。

   沒有一次是「規則錯、別的訊號對」。

## 四、建議：三層自動化，AI 只動第三層

```

  │
  ├─ ① 修正 chips 比對 bug        ─→ 77 張（tier4 假異議）直接消失   【零成本，純規則】
  │
  ├─ ② 「只有 Gemini 反對」       ─→ 159 張（70%）自動確認規則標籤    【機械門檻，無 AI】
  │                                  依據：歷史上這種組合規則贏 265/265
  │
  └─ ③ 真有訊號反對（chips/spec/模型）69 張 ─→ 這裡才是 AI 的位置
       ├─ chips 反對 34 張  → 工種層級有衝突， Gemini 只會更糟（它的預測就是被拿來比的那個數字）
       ├─ 模型反對   46 張  → 本地探針說不是這類， SigLIP kNN 投票可給第二意見
       └─ 兩者重疊
```

### 4.1 ② 的門檻怎麼定（可校準，不是拍腦袋）

「只有 Gemini 反對」目前是 `d_gem & ~d_chips & ~d_spec & ~d_model`。
自動確認不是「以後都不用人看」，是**「這種組合連續 265 次都同一個答案，再放 100 張進來才夠翻盤 1 次」**。

門檻要留退路，建議寫成 `src/autoadjudicate.py`：

```
可自動確認  ⟺  反對訊號只有 Gemini 一個
           且  該 (title→cls) 規則在已裁歷史中勝率 ≥ 0.95（樣本 ≥ 20）
           且  該類別在 split 裡存在（不是孤兒裁決）
寫進 review.csv，note 欄標 "auto:gemini-only" 留痕，與人工裁決同檔同格式
```

第三個條件是防 `orphan_reviews()` 那個坑——自動裁決指到不存在的類別會無聲消失。
`note` 欄讓你隨時能把自動裁決全撈出來回滾（`save_review` 已是 append-only，符合現有架構）。

### 4.2 ③ 的 69 張：為什麼現有的兩條 AI 路都不夠

**Gemini 路（文字）**：③ 裡 chips 反對的那 34 張，Gemini 的答案**就是那個被比對的欄位**。
拿「被質疑的證人」當仲裁者，邏輯上繞不出來。它的價值在 ②（過濾），不在 ③（判斷）。

**kNN 路（視覺）**：我在 22 張待裁孤兒上跑了 SigLIP 最近鄰加權投票：

```
平均最近鄰 cosine 0.807（很高，鄰居確實長得像）
但投票結果：      「1F公設大廳嵌入式除塵地墊」→ 一張投 地磚貼飾、一張投 鋁門窗
                  「監控影像角度調整」    → 一張投 地磚貼飾、一張投 外牆磁磚
                  「B3F車道捲門」      → 投 雜項-清潔（兩張都投錯，top1 sim 0.85）
```

**最近鄰照片「長得像」，不等於「同類」**——監控照片的鄰居是同工地同時段的其他工序。
kNN 對這批的精度不到一半，不能當裁決者，只能當**提示**。

**真正缺的第三條路：VLM 看圖說工種。**
③ 裡 chips 反對的 34 張是「工地主任打的驗收項目說 A，title 說 B」——
這題的答案在**照片裡**，不在文字裡。你 ROADMAP 已有 `gemma4:e4b`（本地唯一 VLM），
也有尺入鏡 PoC 成功的先例（B→A 降格）。建議：

```
③ 的 34 張 chips-反對 → 餵 gemma4:e4b 出「閉集合選答」（只給 split 裡的類別選，不准自由作答）
                       題目帶 title 與 chips 的衝突當 context：「title 說 X，查驗重點說 Y，照片是哪個？」
                       答案不直接採信，標成第 5 層「VLM 有異議」進佇列，人看最後一眼
```

關鍵在**閉集合**：Gemini 之所以 16% 對率，部分原因就是它自由作答（`predWorkItem` 原文是
「泥作粉刷工程」「輕隔間批土工程」這種粗粒度自由文字，再套規則正規化，兩次轉換兩次失真）。
閉集合 + 帶衝突 context，比自由作答約束強很多。

## 五、孤兒院：不是「要不要自動化」，是三種完全不同的東西混在一個佇列

先把 8 張（今天同步後的數字，前次是 22）拆開——它們看起來都叫「孤兒，其實是三件事：

| type | 判準 | 張數 | 是什麼 | 該怎麼辦 |
|---|---|---|---|---|
| **A 新工種候選** | 有 `chipsOn`（主任親筆查驗重點） | 6 | 真施工照，規則缺一條 | 補 `labels.yaml` 規則，或湊 12 張開新類 |
| **B 訪查/巡視** | 無 `chipsOn`、無 `predWorkItem` | 2 | 根本不是工種照片 | **標排除，移出訓練語料** |
| **C 標題語意模糊** | 有 `chipsOn` 但落在 fallback | 0 | 規則該接沒接 | 補規則 |

**B 只有兩張，而且是同一個 title「高雄厝評選」**——`stage: TO_HANDOVER`、沒有 chipsOn、沒有 predWorkItem。
這就是「與工種訓練無關的一般訪查照片」的確切特徵：**日報系統在這張照片上沒有記錄任何工項語意**，
兩個獨立欄位（人打的、Gemini 答的）同時告訴你「這張沒有工項」。

### 5.1 怎麼標示——三種做法，選第三種

**❌ 方案一：標成 fallback「其他」。**
`labels.yaml` 已經實渉過這條路：`drop_fallback: true` 就是為了擋它，因為「其他 = 一袋雜物」
（top-1 0.760 → 0.699）。訪查照混進去只會污染那一袋。

**❌ 方案二：在 `labels.yaml` 加一條 `雜項-訪查` 類別。**
違反你自己的 v6 紀律——「樹上查得到才收」。而且它會被 `min_class_size` 留下來當一個正經類別學，
等於教模型「這是一種工種」。它不是。

**✅ 方案三（建議）：junk_patterns 加一條，讓它回 `None` 被整份排除。**

`labels.yaml` 已經有這個機制，而且**已有完全同性質的先例**——`junk_patterns` 第二條註解寫得明白：
「舊 pptx 帶進來的非工項投影片：拍的是查驗表單、人數、驗收文件，**不是施工畫面**」。
「高雄厝評選」和「江董視察交辦事項」（已在 `junk:`）是同一類東西，只是當初只收了那一個詞。

```yaml
junk_patterns:
  - "^[^\\u4e00-\\u9fff]+$"
  - "自主查驗|人數清點|工地消毒|雨汙水驗收|放樣|進度|會勘|勘驗|消防檢"
  # 訪查/評選/巡視類照片：沒有 chipsOn 也沒有 predWorkItem，日報沒記錄任何工項語意。
  # 與「江董視察交辦事項」（junk）同性質——那是巡視交辦，這是評選活動。
  # 不是「雜項」：它不是工種，丟進 fallback 會污染「其他」那袋。
  - "評選|評審|視察|巡視|參觀|觀摩|典禮|動土|上樑"
```

**為什麼 junk 而不是 review.csv**：`labeler.apply` 裡 junk 讓 `label()` 回 `None`，
照片在 `out = out[out.cls.notna()]` 就被排掉，**不進訓練、不進評估、不進複核佇列母體、
也不進 `cvat_export`**（它吃 `Labeler.apply` 的結果）。一次乾淨。
而 `review.csv` 的覆蓋是**類別**級的（`cls` 塞一個值），機制上只能蓋成某個類，蓋不成「排除」。

**人工覆蓋的優先權仍然在最上**：`apply` 在 junk 過濾**之前**套 review.csv，所以
「這張訪查照其實有拍到工項」可以被你手動救回來——寫一列 review.csv 就收回來，架構不變。

### 5.2 更穩的做法：不要只靠 title，用「雙欄位空白」當訊號

title 裡有沒有「評選」這個詞，其實是脆弱判準（下次來一張叫「評鑑」就漏了）。
真正穩的是那兩個獨立欄位同時空白：

```
無 chipsOn（主任沒打查驗重點）
且 無 predWorkItem（Gemini 也判不出工項）
→ 這張照片在日報系統裡「沒有工項語意」
```

這是**兩個獨立觀察者都說沒訊號**，比任何 title 關鍵字都可靠，而且它自動涵蓋未來的新詞。
建議把這個條件做成孤兒偵測的一個分流：

```python
# core/review_utils.orphans 附近
no_trade_signal = orph.chipsOn.isna() & orph.predWorkItem.isna()
# 這批不是「缺規則的施工照」，是「沒有工項語意的照片」→ 建議排除，不進新類候選
```

在 UI 上它該長成「這張不是施工照」的標示（而不是「歸哪個類別」的選單），
點下去寫一個標記把它從語料移除。**現在的孤兒院只有「畢業到某個類別」這一個動作，
缺一個「這張本來就不該在這裡」的動作**——這正是你問題裡「要怎麼標示」缺的那一塊。

### 5.3 數字小結

```
8 張待裁孤兒
├─ 6 張 A（真施工照，缺規則）→ 補 labels.yaml，或留著湊 12 張開新類
└─ 2 張 B（高雄厝評選 ×2） → junk_patterns 排除，不進任何語料
```

注意比例：**B 只佔 2/8**。前次同步是 22 張時，`chipsOn` 空白的同樣只有 2 張（同一個 title）。
**「孤兒院越來越大」的成長來源是 A（新工種），不是 B（訪查照）。**
所以這個排除機制是**正確性**修正（別讓無關照片混進語料），不是**減量**手段——
減量要靠 A 補規則，和 §四 ② 的自動裁決。別把兩件事的期待混在一起。

## 七、為什麼不直接「讓 Gemini 裁掉所有」

你的問題是「怎麼讓 AI 介入判斷」。數據說的答案是反過來的：

**在這個佇列裡，Gemini 是被審的對象，不是審判者。**

- 它的答案已被拿來當 tier 的計算材料（`predWorkItem` → `gemNorm`），再拿它仲裁 = 循環。
- 歷史對率 16%，規則 100%。
- 265 張已裁裡，只有 43 張人類最後採用了 Gemini 的答案，而這 43 張**全部**與規則標籤重合
  （規則也對，不是 Gemini 救回來的）。

**AI 介入的正確位置**：把 ② 的 159 張「垃圾異議」用規則自動消滅（不需要 AI），
把 AI 省下來給 ③ 的 69 張——那裡需要**看圖**，而現有的 SigLIP 探針 + Gemini 文字都不看圖。
這才是你 ROADMAP 裡 gemma4:e4b 該打的仗，而且是閉集合、帶衝突 context 的版本，不是自由作答。

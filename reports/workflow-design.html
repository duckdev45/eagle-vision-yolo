01老闆問的三件事

「有沒有 workflow design」通常是在問這三題。誠實的答案是一綠、一黃、一紅。

這是可重複的流程，還是某個人手動跑出來的？

可重複

七階段全是 CLI；切分凍結在 JSON；13 份實驗結果連同設定存檔在 reports/。換一台機器照著附錄跑得出同樣的數字。

誰按按鈕、多久跑一次、什麼時候自動重訓？

只有同步自動化

資料同步是 cron 每日 08:00。訓練與評估目前全手動，沒有觸發條件——資料長了不會有人被通知。

出問題怎麼發現、怎麼回退？

尚未定義

沒有 model registry、沒有上線門檻、沒有 rollback 程序。第 05 節是補齊計畫。

02四條鐵律

不是風格偏好，是踩過坑之後定下來的。每一條都有對應的測試在 tests/test_core.py 擋著。

一、raw/ 不可變，derived/ 隨時可重建分類規則還沒定案，下載時就分資料夾等於每改一次規則要重抓幾百張。結構用 symlink 放在 derived/tree/，重建成本為零。
二、前處理必須與標籤完全無關所有照片一視同仁遮蔽，包含本來就乾淨的圖。否則「四角是不是灰的」本身就成了洩漏訊號。
三、畫面幾乎相同的照片不可跨 train／test日報按「工地 × 日期」整天切；QMS 按「格」整格切（一格是同位置同時間拍的 2~3 張）。隨機切會讓測試集裡出現訓練集的近乎同一張。
四、每個實驗都要有對照組；下判斷看分組交叉驗證，不看單一數字測試集只有 99 張，1 張 = 1.0pt。單一固定切分只用於跨次比較，不用於下結論。理由見第 04 節。

04為什麼「分數變高」目前還不能當證據

測試集 n = 99，一張照片 = 1.0 個百分點。下圖是各實驗的 95% 信賴區間。

這一節就是缺口 G1 的全部理由。在測試集擴大到能分辨 3pt 差異之前，任何「模型變聰明了」的宣稱都不成立。而且每改一次 labels.yaml，測試集本身就換一份（489 → 457 → 441 張是三份不同的考卷），分數更不可比。

05缺口與補齊順序

流程的骨架是完整的，缺的是「上線」與「持續」這兩段。

優先缺口為什麼重要建議做法
P0G1 沒有凍結的黃金測試集 99 張、區間 ±8pt；且每改一次標籤規則考卷就換一份，分數不可比 300–500 張人工標、分層抽樣、獨立於 labels.yaml；兩人各標一次算一致度，順便得到人類天花板
P0G2 沒有上線門檻 「什麼分數才能上線」沒有定義，等於每次都靠開會決定 見第 06 節。主指標從 top-1 改成 coverage @ precision ≥ 0.90，判定用分組 CV 而非單點
P0G3 沒有線上回饋迴路 使用者在產品裡修正工種的行為 = 免費的真實標籤，目前完全沒收 產品端記 override log（改前／改後／modelVersion）→ 回流成訓練資料，同時當線上準確率的代理指標
P1G4 沒有自動重訓觸發 只有資料同步有 cron，資料長了沒人知道該重訓 新增 ≥ 200 張 或 覆寫率週對週上升 ≥ 5pt 或 每月一次，取先到者
P1G5 沒有 model registry／rollback models/ 是一坨檔名，沒有「現在線上是哪一個」的指標 registry.json 記每個候選的指標與門檻結果 + 一個 current 指標。回退 = 改一個欄位
P1G6 config.json 沒記 code 版本 無法重現「那次實驗是哪份程式碼」 加 gitSha / uv.lock hash / seed
P2G7 14 個測試要手動跑 洩漏防護只在有人記得跑的時候有效 pre-commit hook 或 CI 跑 tests/test_core.py

Promotion gate（草案，數字待 G1 完成後校準）

檢查門檻為什麼
黃金測試集 coverage @ precision ≥ 0.90不低於現行版本 − 2pt這才是產品指標：自動填掉多少、填的裡面對多少
分組交叉驗證 macro-F1不低於現行版本 − 1σ防止單點運氣
每一類的 recall沒有任何類別掉到 0防止小類被犧牲換總分
洩漏測試test_core.py 全綠切分與遮罩的鐵律
前處理一致性離線 vs ONNX 預測一致率 ≥ 99.5%線上／離線落差最常見的來源
影子模式對照與現行版本分歧率 < 15%，且分歧樣本人工抽檢 30 張判定不更差上線前最後一道

上線與回退

  • 串接，不取代。prob ≥ τ 用本地模型，否則打 Gemini。兩邊錯的照片重疊不高，且本地模型只有 10 類、目前沒有「以上皆非」——硬取代會在看不見的地方變差。
  • 獨立小服務（FastAPI + onnxruntime），掛在現在呼叫 Gemini 的那個點旁邊。獨立才能獨立回退。
  • 推論輸出必須帶版本：{cls, prob, modelVersion, labelsVersion, encoderVersion} 全部寫進 DB。沒有這個，三個月後無法回答「這張是哪個版本判的」。
  • 回退是改一個數字：把 current 指回上一版，或把 τ 調到 1.0——等於完全回到現在純 Gemini 的狀態。
  • 監控：各類別的使用者覆寫率（線上真實準確率的免費代理）· 低信心比例的走勢（突然上升 = 進到新工序或新建案）· 預測分佈漂移。

07已封板的結論

這四條有實驗證據，不需要重新討論。

結論證據
QMS 那 36k 張對「日報工種辨識」沒有幫助。三條路都試過：混訓、純遷移、預訓練。 混訓 0.687 / 純遷移 0.283 / 兩階段微調 0.748，全部低於什麼都不做的 0.818。劑量曲線單調下降（加 0 → 342 → 700 → 1,165 張：0.768 → 0.707 → 0.626 → 0.596）
原因是領域偏移，不是資料品質。稽核照是「查驗點特寫」，日報照是「工人在現場施工」的廣角。 QMS 自己學自己學得起來：線性探針 0.680 → 微調 0.884（n = 2,204、區間僅 ±1.4pt）。編碼器一鬆綁就吃得下那個領域，只是吃不到日報這邊
統一遮罩的代價不值得，已回退。 兩邊都遮成「四角 + 左下」→ 日報基準線 0.818 → 0.768（−5pt）。改成兩階段微調後洩漏顧慮消失
不取代 Gemini，用信心門檻串接。 兩邊錯的照片重疊不高；QMS 母體顯示實際被拍的工種有 47% 落在這 10 類之外
副產品值得單獨一提：backbone-qms（0.884 / 26 個中類 / 已匯出 ONNX）本身就是一條獨立的產品線——QMS 稽核照自動分類。它不該被當成日報實驗的失敗品埋掉。
